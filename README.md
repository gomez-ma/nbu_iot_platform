# NBU IoT Platform — Phase 1

Platform foundation for PostgreSQL, user authentication, organizations, projects, role based permissions, and an admin console.

## What is included

- Email and password registration and login with Argon2 password hashing and signed bearer tokens.
- Organization workspaces and projects with scoped membership.
- Organization roles: `owner`, `organization_admin`, `member`, and `viewer`.
- Project roles: `project_owner`, `project_admin`, `project_member`, and `project_viewer`, managed separately for each project.
- Permission catalog and role-to-permission mappings stored in PostgreSQL.
- Responsive Thai admin console at `/` for account access, organizations, projects, and members.
- Versioned PostgreSQL schema managed by Alembic.
- Device registry, EMQX-managed MQTT credentials and per-device topic ACLs, with event-driven connection status and telemetry heartbeat tracking.

## Run with the supplied EMQX/PostgreSQL compose setup

The app container joins the existing external Docker network `iot_default` and connects to PostgreSQL using the service hostname `postgres`. Start the supplied infrastructure compose project first, with its `.env` and `database/init.sql` beside that compose file. Copy `database/init.sql` from this project next to the supplied compose file; Alembic owns the application schema. Since that compose declares its network external, create it once if it does not exist with `docker network create iot_default`.

Create a local `.env` from `.env.example`, set a unique `SECRET_KEY`, and set database values to match the supplied PostgreSQL `.env`. Then run from this directory:

```powershell
docker compose --env-file .env up --build -d
```

Open <http://localhost:8000>. Register the first account; it becomes the platform administrator and can create an organization as its owner. Existing installations without a platform administrator bootstrap the earliest registered account on startup. Platform administrators can search accounts and suspend or reactivate them from the account menu. To add someone to an organization, that person first creates an account, then the owner/admin can add their email from the organization card.

Set `EMQX_BASE_URL` to the broker's Dashboard API address reachable from the app container (default `http://emqx:18083`). `EMQX_USERNAME` and `EMQX_PASSWORD` provide the Dashboard account used to obtain a short-lived REST API token. The compose file can reuse `EMQX_DASHBOARD_PASSWORD` from the supplied infrastructure `.env`.

For a local Python run, install `requirements.txt`, set `DATABASE_URL` to a reachable PostgreSQL server and `EMQX_BASE_URL`/`EMQX_USERNAME`/`EMQX_PASSWORD` to the broker API, run `alembic upgrade head`, and start with `uvicorn app.main:app --reload`. `EMQX_DASHBOARD_PASSWORD` is accepted as an alternative password variable. OpenAPI documentation is at `/docs`.

## Data model

```text
users ──< organization_members >── organizations ──< projects
                         │
                         └── roles ──< role_permissions >── permissions
```

Organization membership is required before assigning a user to a project. Project membership is unique per user and project, and access to projects and devices is checked against the organization and project roles on each API request. Existing projects are migrated with their creator as project owner and current organization members assigned a matching project role.

## Main API

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/api/v1/auth/register` | Create an account |
| POST | `/api/v1/auth/login` | Sign in |
| GET | `/api/v1/auth/me` | Current account |
| GET/POST/PATCH/DELETE | `/api/v1/organizations` | List or create organizations; patch or delete a specific organization at `/{id}`. Deleting an organization also deletes its projects and memberships. |
| GET/POST/PATCH/DELETE | `/api/v1/organizations/{id}/members` | List or add members; patch/delete a specific member at `/{user_id}` |
| GET/POST/PATCH/DELETE | `/api/v1/organizations/{id}/projects` | List or create projects; patch or delete a specific project at `/{project_id}` |
| GET/POST | `/api/v1/organizations/{id}/projects/{project_id}/members` | List or assign project members by account email |
| PATCH/DELETE | `/api/v1/organizations/{id}/projects/{project_id}/members/{user_id}` | Change a project member's role or remove them |
| GET | `/api/v1/health` | Health endpoint |

## Phase 2 — MQTT & Device Management

- Register devices within a project. Client IDs are generated by default or can be supplied at registration.
- The first device registration creates the EMQX password-based built-in authenticator using Client ID as the identity, or updates an existing built-in authenticator from `username` to `clientid` while preserving its password hash and other settings. It also creates/enables the built-in authorization source. The platform orders these sources before existing sources so device rules are evaluated first.
- MQTT passwords are generated at registration and rotation, stored as Argon2 hashes in PostgreSQL, and returned once to the caller. EMQX stores its own hashed credential.
- MQTT topics use `{organization_slug}/{project_slug}/{device_topic_name}/{client_id}/...`, without a platform prefix or a `devices/` segment. `device_topic_name` is created from the device name and updates with it; the platform rewrites project ACLs and disconnects affected clients, so firmware must be updated to use the new topic. For example, a device named `ESP32_001` with Client ID `nbu_1_abc123` publishes telemetry under `nbu-research-lab/smart-home/ESP32_001/nbu_1_abc123/telemetry/#` and subscribes to `nbu-research-lab/smart-home/ESP32_001/nbu_1_abc123/commands/#`.
- Each device starts with publish access to its own `telemetry/#` and subscribe access to its own `commands/#`, plus a deny rule for all other topics. Additional ACL rules can target the topic namespace of any registered device in the same project and must include that target device's exact Client ID. To send a command from `ESP32_002` to `ESP32_001`, grant `ESP32_002` Publish access to `nbu-research-lab/smart-home/ESP32_001/{ESP32_001_client_id}/commands/#`; `ESP32_001` subscribes to the same topic.
- The project device control shows MQTT online/offline status. EMQX client connect/disconnect events are delivered to the app and pushed to open browser sessions over authenticated Server-Sent Events (SSE); the page does not poll or redraw every few seconds. Connection status is `unknown` when EMQX cannot be reached during the initial/manual device list refresh.
- The app creates or updates its EMQX HTTP connector, actions, and rules when a device list is opened or a device is registered. The webhook URL defaults to `http://nbu-iot-platform:8000`, so the app container must share a Docker network with EMQX; set `DEVICE_EVENT_WEBHOOK_URL` if the broker needs another reachable address. Webhook requests are authenticated with a key derived from `SECRET_KEY`. SSE fan-out is in-process and fits the supplied single-Uvicorn-worker deployment; multi-worker or multi-instance deployments need a shared event bus before scaling out.

The Overview online-device list is paginated on the server (25 by default, configurable to 50 or 100), searchable by device name or Client ID, and filterable by organization and project.

## Remaining platform work

Email invitations/verification, password recovery, audit history, email notifications, and multi-instance event fan-out are not included yet. Account registration is open in this iteration. Before public deployment, set a strong secret, terminate TLS at a trusted proxy, add email verification and password recovery, and review registration policy.
